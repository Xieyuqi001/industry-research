# 实现总览

> 本文描述**实际存在并已跑通**的系统。`docs/archive/` 里那批 2025-08 的草稿描述的是另一套
> （LangGraph 编排 / GPT-Researcher fork / pgvector / RAGAS 金标准集）——**那套从未被实现**，
> 保留仅为存档，不要照它做。

## 一句话

两个 Claude Code skill：`industry-research` 负责**从零产出一份跨国行业研报**，
`report-html` 负责**把这份研报变成能直接看的网页**。前者写完 `.md` 会自动调后者。

## 上下文：为什么是「skill」而不是「框架」

最初的设想是搭一个带向量库、检索编排、自动评测的独立系统。实际做下来，
**绝大部分复杂度不在「检索基础设施」，而在「判断」**：

- 哪个数字口径可信、哪两个数矛盾了
- 这条来源是研报还是软文、是今年的还是三年前的
- 同一个「中国市场份额」两个来源给了 29% 和 33%，是取平均还是并列

这些恰恰是 LLM 擅长而流水线不擅长的。所以终态是**把判断留给模型、把纪律写成 skill**：
skill 规定**做什么、按什么顺序、什么算不合格**，模型负责执行与判断。

代价要讲清楚：**这套没有确定性保证**。同一行业跑两次，来源数量和措辞会不同。
它换来的是零基础设施、零依赖、一个下午能改。

### 为什么「主 agent 搜、子 agent 只读」

子 agent 并行跑，如果每个都去搜公众号，会**同时**撞上搜狗的请求指纹门禁和验证码；
而且它们互相看不见对方在搜什么，必然重复。

所以检索**上收**到主 agent 串行做（可控限流 + 单点熔断），
子 agent 只负责**读 + 判断**。这条分工是实测逼出来的，不是设计洁癖。

## 端到端流程

| 步 | 谁做 | 产出 | 为什么这么切 |
|---|---|---|---|
| 0 | 主 agent | 要不要完整研报 | 防止用户只是随口一问就被跑满检索 |
| 1 | 主 agent | 市场范围 + 深度档位 | 工作量差 5 倍以上，必须先定 |
| 2 | 主 agent | 一句话行业边界 | 「含什么/不含什么」不定，后面每个国家各理解一套 |
| 3 | 主 agent | 全球总量锚点 / 国别识别 / 供应链依赖 | **这三样子 agent 给不了**——它们只查本国，给不出分母和跨国关系 |
| 4 | 子 agent ×N | 六模块 findings + sources | 并行，一国一个，互不干扰 |
| 5 | 主 agent | 跨国对比 | 估值对标、格局拆分必须同一口径，只能主 agent 做 |
| 6 | 主 agent | 六节报告 | |
| — | 主 agent | 交付前自检 8 项 | 见下 |
| 7 | 主 agent → report-html | `.md` + `.html` | 自动，不问用户 |

### 交付前自检（8 项，任一项不过先修再交付）

1. 无孤儿数字——每个数字后面都有 `[来源]`
2. 引用 ↔ 附录一一对应（正文引的都在附录，附录无未引用条目）
3. 来源字段完整（标题+发布方+日期+URL，URL 必须实际访问过）
4. 事实 / 观点 / 预测标注一致
5. 国别覆盖完整，无空壳国家
6. 时效显式（开头注明数据截至日）
7. **跨章节一致**——跨国对比里的数字与国家章节里的同源数字不矛盾
8. 免责声明在文末

第 2 项和第 7 项是**返工率最高**的两项。第 7 项尤其：同一份报告里
「中国占 29.1%」和「中国占 33%」并存，通常不是笔误，而是**两个来源口径不同**——
这种情况**不要取平均**，要并列并标注口径差异（示例报告里就有三处这样的显式处理）。

## 为什么 `report-html` 要独立成 skill

因为它跟行业无关。任何 Markdown 长文档都能用，所以单独一个 skill、
`industry-research` 在步骤 7 调它。分开的另一个好处是**改样式不用碰主流程**：
配色/字号/目录宽度全在 `theme.css` 顶部的变量区，改完重跑 `build.py` 就生效。

它跟「用 pandoc」的区别在于**自检**：`build.py` 在写出前会检查
悬空引用（正文引了 `[X9]` 但附录没这条）、残留未转换的 Markdown、输出是否真的自包含，
**不过就不写文件**。所以它不会产出「看起来成了、其实引用全断」的页面。

## 已定决策

| 决策 | 理由 |
|---|---|
| 用 skill，不用独立框架 | 复杂度在判断不在基础设施；零依赖、可读可改 |
| 子 agent 只读不搜 | 并行搜索会同时撞限流、且必然重复 |
| 检索上收到主 agent 串行 | 限流与熔断需要单一控制点 |
| 引用 ID 按国别加前缀（C/U/E/T/J/K/I） | 各国子 agent 各自从 1 编号，不加前缀必然撞车 |
| 非中国来源池不设硬时效门槛 | 设了直接归零；改为**按用途分级**（≤90 天=最新进展 / ≤1 年=近期观点 / >1 年=仅作背景） |
| 交付前自检 8 项写进 skill | 不写下来，模型会跳 |
| 样式全部集中在 `theme.css` | 改样式不该碰转换逻辑 |

## 已知风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| 搜狗验证码（累计查询量触发） | 高 | 查询数封顶、组间 `sleep 12`、遇 CAPTCHA **立即熔断整轮**；已拿到的国家池照发，缺的转 `site:` 并在报告末尾披露 |
| 公众号旧文被当「最新」 | 高 | 强制核 `create_time` + 核对账号主体（软文 vs 研报） |
| 子 agent 静默编造 URL | 高 | 硬性要求「url 必须是实际访问过的」；靠摘要拿到的必须标「摘要获取、未核验原文」 |
| 同一指标多来源口径冲突 | 中 | 不取平均，并列 + 标注口径（示例报告有三处） |
| 墙外站不可达（Reuters 等） | 中 | 换可达源，或在报告里如实标注该条未核验 |
| WebFetch 抓不到公众号正文 | 中 | 改用 `curl` + 浏览器 UA（差别在请求指纹，不在 IP） |

## v1 边界（明确不做）

- **不做自动评测 / 金标准集**——没有确定性输出，评测本身先要解决一致性问题
- **不做增量更新**——每次重跑是全新的一份，不做「在旧报告上打补丁」
- **不做交互式问答**——产出的是一份静态报告，不是可追问的知识库
- **不做图表**——表格为主，图表要额外引入渲染依赖，与「零依赖」冲突
- **不做公众号付费文章**——微信未开放解析接口，明确拿不到
