# 行业调研助手 · 工具架构调研报告

> 状态：调研初稿（基于 web 检索与领域知识整理）
> 日期：2025-08

## 1. 参考产品与开源项目

### 1.1 大厂 "Deep Research" 型产品

| 产品 | 思路 | 优劣势 | 对我们系统的启示 |
|------|------|--------|------------------|
| OpenAI Deep Research | 多轮自主检索→长报告，带引用 | 质量高、贵、黑盒 | 报告结构与引用规范值得模仿 |
| Gemini Deep Research | 类似，深度集成 Google 搜索 | 检索能力依赖 Google 生态 | 可外包单次深度调研任务 |
| Perplexity | 检索→合成，引用内联 | 轻量、快 | 引用内联（[n]）交互范式 |
| Manus | 通用自主智能体（多步任务） | 通用但不可控 | 警示：自动化≠可控，审查必须内建 |
| Elicit / Consensus / SciSpace | 学术文献检索与总结 | 专注文献 | 学术渠道的子模块参考 |

这些产品证明：**「检索→规划→多轮验证→带引用成稿」的流水线范式是行业共识**。它们的共同短板（对个人用户）是黑盒、不可定制、成本高——这正是自建的意义。

### 1.2 开源项目（直接可借鉴）

| 项目 | 架构要点 | 可借鉴处 | 局限 |
|------|----------|----------|------|
| **GPT-Researcher**（assafelovic） | 规划（plan agent）→ 并行研究（research agents，用 Tavily/Serper 等）→ 写作（writer）；新版用 LangGraph 编排多智能体 | 完整流水线、检索集成、引用管理、可自托管 | 检索深度一般、中文支持需调优、事实核查弱 |
| **STORM**（斯坦福，arXiv 2402.14207） | 两阶段：① 预写阶段（发现资料→生成大纲）② 写作阶段（多视角 RAG，模拟多角色提问迭代） | **大纲驱动** + 多视角提问 = 报告结构化与覆盖面提升 | 主要用于百科类长文，行业数据类需改造 |
| **Firecrawl** | 网页→Markdown、整站爬取 | 采集层免维护 | 是工具不是系统 |
| **MiniPerplx / 各类 Perplexity 开源复刻** | 检索→RAG→流式回答 | UI 与交互参考 | 非报告型 |
| **RAGFlow / Dify / Coze** | 可视化 RAG 与智能体编排 | 快速原型；RAGFlow 文档解析强 | 深度定制受限 |

**结论**：不建议从零写流水线。**MVP 推荐基于 GPT-Researcher（或取其规划+研究+写作骨架）二次开发**，叠加 STORM 的「大纲先行」思路与自建审查层。

### 1.3 多智能体编排框架对比

| 框架 | 定位 | 适用场景 | 备注 |
|------|------|----------|------|
| **LangGraph** | 图状工作流，状态机 | 复杂多阶段流水线 | GPT-Researcher 新版即用它；可控性强，推荐 |
| **CrewAI** | 角色化智能体（crew） | 角色分工明确的任务 | 上手快，抽象层高 |
| **AutoGen / AG2** | 多智能体对话 | 辩论/批判模式研究 | 对话式协作 |
| **LlamaIndex** | 数据框架 + AgentWorkflow | RAG 深度集成 | 检索侧强 |
| **Haystack** | 检索流水线 | 生产级 RAG | 与 LangChain 并存 |
| **Dify / Coze** | 低代码平台 | 快速原型/非工程师 | 便于产品化 UI |

**建议**：LangGraph 为主（控制流清晰、可测试），检索层用 LlamaIndex 或直接调检索 API，避免全栈绑定单一框架。

## 2. 调研流水线（Pipeline）设计

行业共识的八阶段流水线：

```
① 需求理解/问题拆解 → ② 研究规划（大纲+检索计划）
→ ③ 资料发现与检索 → ④ 数据采集与清洗
→ ⑤ 信息抽取与整理（证据卡） → ⑥ 多源分析与交叉验证
→ ⑦ 报告生成（带引用） → ⑧ 质量审查 → 交付（MD/PDF/Word/PPT/网页）
```

各阶段要点：

| 阶段 | 关键设计 | 产出物 |
|------|----------|--------|
| ① 问题拆解 | 把宽泛问题（"新能源行业怎么样"）拆成可检索子问题（政策/市场/技术/竞争/企业） | 问题树 |
| ② 规划 | 大纲先行（STORM 思路）：先出骨架再填内容 | 报告大纲 + 检索计划 |
| ③ 检索 | 多源并行检索（官方+新闻+研报+学术），去重 | 候选文档集 |
| ④ 采集 | 网页→Markdown（Firecrawl/Jina）、PDF 解析（表格抽取）、去重 | 干净语料 |
| ⑤ 抽取 | 提取"主张+数据点+来源"，形成**证据卡（evidence card）** | 证据卡库 |
| ⑥ 交叉验证 | 多源比对、异常值检测、口径核对（衔接审查机制） | 验证结果标注 |
| ⑦ 生成 | 按大纲逐节生成，内联引用 [n] | 草稿 |
| ⑧ 审查 | 事实/引用/一致性检查（见 03） | 终稿 |

> 关键工程原则：**把「检索到的材料」与「生成的内容」分离存储**——证据卡是生成的事实底座，这让审查与追溯成为可能。

## 3. 多智能体协作模式

| 模式 | 说明 | 适用 |
|------|------|------|
| 角色分工（planner/researcher/writer/reviewer） | 各司其职，数据契约传递 | 推荐主模式 |
| 并行研究（fan-out） | 多个 researcher 并行检索不同子问题 | 提升速度 |
| 辩论/批评（critic/referee） | 写作智能体与审查智能体互相挑错，多轮 | 质量关键环节 |
| 层级拓扑（supervisor 调度 worker） | 主管拆任务、汇总 | 大规模调研 |
| LLM-as-judge | 用强模型评审弱模型输出 | 评估环节 |

**推荐拓扑**：`主管(planner) → 并行研究员(researchers) → 分析师(analyst) → 写作员(writer) → 审查员(reviewer) → 审核门(human)`。
其中**审查员独立于写作员**（不同模型/不同 prompt），避免自说自话。

## 4. RAG 设计

| 环节 | 推荐方案 | 说明 |
|------|----------|------|
| 采集 | Firecrawl / Jina Reader / 官方 API / PDF 解析 | 转 Markdown/结构化 |
| 分块 | 语义分块（按标题/段落），512-1024 token | 行业报告表格多，**表格单独处理** |
| Embedding | 中文：bge-m3 / text-embedding-v3（阿里）/ BAAI；国际：OpenAI text-embedding-3 | 中文场景必须选中文优化模型 |
| 向量库 | **Qdrant / Milvus / pgvector**（小规模选 pgvector 最省事） | 规模小时 SQLite-vec 亦可 |
| 混合检索 | BM25（关键词）+ 向量（语义）+ **重排序（rerank，如 bge-reranker）** | rerank 对质量提升明显 |
| 知识库维护 | 增量入库、来源去重、版本管理、过期标记 | 资料快照与更新策略（见 §6） |
| 引用回溯 | chunk → 文档 → URL/页码 三级映射 | 报告引用可点回原文 |

## 5. 长上下文与报告生成

- **长文档策略**：map-reduce 逐节生成 → 合并 → 一致性修订；不把全部资料塞进一个上下文。
- **结构化输出**：用 JSON Schema 约束抽取结果（证据卡、数据点），保证下游可处理。
- **引用管理**：统一 `[n]` 编号 + 文末来源清单（URL、标题、抓取时间、信源等级）。
- **报告模板**：Markdown 为母版，可转 Word（pandoc）/ PDF（weasyprint / typst）/ PPT（python-pptx）。
- **中间产物可编辑**：大纲、证据卡、数据表均落盘为可审阅文件——这是人工审核的基础（见 03）。

## 6. 自动化与运维

| 需求 | 方案 | 说明 |
|------|------|------|
| 定时触发 | cron / GitHub Actions / n8n | 日报/周报/月报 |
| 事件触发 | 监控公告/政策源（巨潮、部委官网）变化 → 触发调研 | 财报季、新政发布自动生成快评 |
| 增量更新 | 知识库去重 + 指纹；只重检索新增内容 | 控制成本 |
| 存储 | 文件 + SQLite（元数据/证据卡）+ 对象存储（语料快照） | 小规模够用 |
| 版本控制 | git 管理报告与脚本；每次报告记录输入（prompt/检索集）哈希 | 可复现性 |
| 成本控制 | 模型分层（贵模型做规划/审查，便宜模型做抽取/改写）；token 预算；缓存检索结果 | 一份报告成本可控制在几元~几十元 |
| 可靠性 | 每阶段失败重试、断点续跑、超时熔断 | 检索 API 偶发失败需容错 |

## 7. 模型选型

| 场景 | 推荐模型 | 理由 |
|------|----------|------|
| 规划/审查（复杂推理） | DeepSeek-R1 / Claude Sonnet / GPT-4o 级 | 推理强 |
| 抽取/改写（批量） | DeepSeek-V3 / Qwen / GLM / Kimi | 便宜，中文好 |
| 检索增强回答 | 同上分层 | — |
| Embedding | bge-m3 / 阿里 text-embedding-v3 | 中文优化 |
| Rerank | bge-reranker-v2-m3 | 中文优化 |

**要点**：
- 中文行业调研：国产模型（DeepSeek、Qwen、GLM、Kimi）性价比高，DeepSeek 长上下文与推理模型尤其适合长报告。
- **模型分层是成本控制核心**：同一流水线内按任务难度分配不同模型。
- 数据合规（中国）场景下，国产模型 + 自托管更稳妥（见 03 合规）。

### MVP 第一期功能范围（建议）

1. 手动触发一个调研主题 → 输出带引用的中文 Markdown 报告（30-60 分钟/份）
2. 内置检索层（Tavily/Serper + Firecrawl）与官方源/巨潮快照
3. 证据卡中间产物落盘（可人工查看）
4. 基础审查：引用有效性检查 + LLM-as-judge 一致性审查
5. 成本估算：单份报告约 2-20 元（取决于检索量与模型分层）

> 不建议第一期就做：社媒爬虫、付费终端接入、复杂调度器——等流水线跑通再扩展。
