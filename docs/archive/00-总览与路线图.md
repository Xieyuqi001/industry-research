# 行业调研助手工具 —— 调研总览与路线图

> 状态：调研完成（初稿）。三个子报告：资料渠道 / 工具架构 / 审查机制
> 日期：2025-08

## 1. 目标与背景

在本地工作区构建一个「行业调研助手」：以 AI（LLM 智能体）为核心，从多渠道自动采集行业资料，
生成带引用、可追溯、可复核的行业研究报告；后续演进为定时/事件驱动的自动化调研流水线。

本报告是前期调研的汇总，回答三个核心问题：

1. **资料从哪里来**（资料渠道）
2. **系统怎么搭**（工具架构）
3. **怎么保证质量与可信**（审查机制）

## 2. 调研方法

- 三个方向的深度子代理调研（各自基于 web_search 检索 2024-2025 最新信息 + 领域知识）
- 直接网络检索补充（开源项目、产品动态、合规政策）
- 调研产出：`01-资料渠道.md`、`02-工具架构.md`、`03-审查机制.md`

## 3. 核心结论（摘要）

### 3.1 资料渠道

- **分层而非堆砌**：核心层（官方统计、上市公司披露、AI 检索 API）→ 重要层（垂直媒体、研报、招股书、工商数据）→ 补充层（付费终端、咨询机构、社媒）。
- **权威源是锚**：国家统计局/行业协会/交易所披露是交叉验证的基准，必须优先接入并定时快照。
- **自动化入口统一**：Tavily/Serper（搜索）+ Firecrawl/Jina（网页转 Markdown）+ Semantic Scholar/arXiv（学术）即可覆盖 80% 公开检索，无需自建大量爬虫。
- 详见 [`01-资料渠道.md`](01-资料渠道.md)。

### 3.2 工具架构

- **范式共识**：「检索 → 规划 → 多轮验证 → 带引用成稿」是行业标准（OpenAI/Gemini Deep Research、GPT-Researcher、STORM 均为此范式）。
- **不要从零写流水线**：MVP 基于 GPT-Researcher 二次开发 + STORM 的"大纲先行"思路 + 自建审查层。
- **多智能体**：主管(planner) → 并行研究员 → 分析师 → 写作员 → 独立审查员 → 人工审核门；编排用 LangGraph。
- **关键工程原则**：检索材料与生成内容分离——「证据卡」（主张+数据+来源）是生成的事实底座，也是审查追溯的锚点。
- **模型分层控成本**：规划/审查用强推理模型，抽取/改写用便宜模型；中文场景国产模型（DeepSeek/Qwen/GLM）性价比高。
- 详见 [`02-工具架构.md`](02-工具架构.md)。

### 3.3 审查机制

- **自动化负责暴露问题，人工负责裁决关键问题**——纯自动化无法兜底。
- 四道硬约束：RAG 接地 + 强制引用 + 数字来源命中检查 + 无证据即标注（不编造）。
- 交叉验证是行业数据报告的必选项：官方基准 + 三角验证 + 异常值检测 + 口径记录。
- 建立评估集（golden 问答）跑回归测试（RAGAS/DeepEval），防止改动引入新问题。
- 合规底线：只引用不转载、免责声明、审计追踪（输入/检索集/模型版本/审查记录可复现）。
- 详见 [`03-审查机制.md`](03-审查机制.md)。

## 4. 推荐方案概览

### 4.1 技术栈建议

| 层 | 推荐 | 备选 |
|----|------|------|
| 语言 | Python 3.11+（本机 3.9.6，需 pyenv/uv 升版） | TypeScript |
| 编排 | LangGraph | CrewAI / 自研状态机 |
| 检索 | Tavily/Serper + Firecrawl/Jina Reader | Exa |
| 向量库 | pgvector / Qdrant | Milvus / SQLite-vec |
| Embedding/Rerank | bge-m3 / bge-reranker | 阿里 DashScope |
| LLM | DeepSeek 为主（分层调用） | Qwen / GLM / Claude |
| 报告渲染 | Markdown → pandoc(Word/PDF) / typst | python-pptx |
| 调度 | cron / GitHub Actions（MVP） | n8n / Temporal（规模化） |
| 评估 | RAGAS / DeepEval + 自建 golden 集 | TruLens |

### 4.2 架构图

```
调度层 (cron / 手动触发)
   │
   ▼
主管 planner（问题拆解 → 大纲+检索计划，强模型）
   │
   ▼
研究员 researchers（并行 fan-out）→ 检索层(Tavily/Serper+Firecrawl+官方源/巨潮/EDGAR)
   │
   ▼
抽取与分析 → 证据卡(主张+数据+来源) → 向量库(bge-m3 + pgvector/Qdrant, 混合检索+rerank)
   │
   ▼
写作员 writer（按大纲逐节生成，内联引用 [n]）
   │
   ▼
审查层（独立审查员：事实核查/引用校验/数字命中/一致性）→ 人工审核门(HITL)
   │
   ▼
交付 Markdown → Word/PDF/PPT/网页；存储：证据卡库+报告版本(git)+审计日志
```

## 5. MVP 路线图

### Phase 0：需求确认（决策点）

搭建前需要拍板的问题（建议逐条回答，答案将直接影响架构取舍）：

| # | 决策点 | 选项 | 影响 |
|---|--------|------|------|
| 1 | 调研主题范围 | 单行业深度 / 跨行业通用 / 客户定制 | 决定知识库与数据源是否要预配置 |
| 2 | 报告形态 | Markdown / Word / PDF / PPT / 网页 | 决定渲染管线与模板工作量 |
| 3 | 触发方式 | 手动提问 / 定时任务 / 事件触发（财报季、政策发布） | 决定调度组件 |
| 4 | 部署方式 | 本地脚本 → CLI → Web 服务（GUI/API） | 决定框架选型与运维 |
| 5 | 模型预算 | 每份报告可接受的 API 成本上限 | 决定模型分层与 token 预算策略 |
| 6 | 检索范围 | 公开网页为主 / 需接入付费库（Wind、知网等） | 决定数据接入复杂度与合规要求 |
| 7 | 语言 | 中文为主 / 中英双语 | 决定 embedding 与模型选型 |
| 8 | 引用要求 | 每份报告强制带引用与来源清单？ | 决定审查机制强度 |

### Phase 1：最小可用（目标：人工触发，输出带引用的 Markdown 报告）
- 单条流水线：问题 → 规划 → 检索 → 抽取 → 生成 → 引用
- 复用成熟开源（如 GPT-Researcher 或其精简版）快速起步

### Phase 2：质量增强（事实核查、交叉验证、评估集）
- 引用逐条校验、数据多源交叉核对、LLM-as-judge 审查
- 建立领域评估集（golden 问答）与回归测试

### Phase 3：自动化（定时调度、事件触发、增量更新）
- 调度器 + 增量知识库 + 版本管理 + 审计追踪
